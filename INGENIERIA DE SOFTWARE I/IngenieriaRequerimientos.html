3.2 · Recolección

Técnicas de recolección

La recolección —también llamada elicitación— es el proceso de descubrir, mediante interacción con personas y documentos, qué necesidades reales debe satisfacer el software.

◆ Concepto clave

Los usuarios rara vez te dicen literalmente lo que necesitan. Suelen describir síntomas ("el sistema es lento") o soluciones imaginadas ("quiero un botón rojo"). Tu trabajo es llegar al problema real.

Cuatro técnicas fundamentales

  • Entrevistas — conversaciones uno a uno o en grupos pequeños. Permiten profundizar.
  • Cuestionarios — preguntas estructuradas para audiencias amplias.
  • Talleres (JAD) — sesiones grupales facilitadas con varios interesados.
  • Análisis de documentos — revisión de manuales, formatos, normativas, reglamentos.
3.2 · Aplicación

Una entrevista bien hecha

▲ Ejemplo: biblioteca universitaria

Pregunta abierta: "Cuénteme cómo es un día normal en el mostrador de préstamos."

Respuesta reveladora: "Lo más pesado es a las 8 a.m. cuando llegan los alumnos a devolver libros antes de su clase de 9. Si el sistema se cae, formamos colas de 30 personas."

Requerimiento descubierto: el sistema debe tolerar picos de 100 devoluciones en 15 minutos y tener modo offline para registrar cuando la red falle. Esto no habría salido en un cuestionario cerrado.

Buenas prácticas para entrevistar

  • Prepara preguntas, pero no las leas como interrogatorio.
  • Pregunta "¿por qué?" varias veces (técnica de los 5 porqués).
  • Cierra con un resumen verbal: "Lo que entendí es… ¿es correcto?"
  • Nunca entrevistes solo a los jefes: los usuarios operativos conocen los problemas reales.
✓ Regla de oro

En la práctica nunca se usa una sola técnica. Una secuencia típica: análisis de documentos → entrevistas → taller → cuestionario para validar prioridades con población amplia.

3.3 · Modelado

Modelado con UML

El texto en lenguaje natural es ambiguo. Un diagrama obliga a precisar relaciones, actores y secuencias —y revela huecos que el texto oculta.

Diagramas más usados en análisis

ActividadesFlujo paso a paso con decisiones y paralelismoProcesos de negocio complejos

Diagrama de casos de uso · tres elementos

  • Actor: rol externo que interactúa (usuario, otro sistema, tiempo). Se dibuja como un "monito".
  • Caso de uso: objetivo que el actor logra. Verbo + objeto: "Registrar préstamo".
  • Relaciones: include (siempre incluye otro) y extend (lo extiende en ciertas condiciones).
3.3 · Plantilla

Caso de uso en forma textual

El diagrama da la visión panorámica, pero cada caso de uso necesita una descripción textual que sirva como contrato funcional.

▲ CU-03: Registrar préstamo

Actor principal: Bibliotecario.

Precondición: El bibliotecario está autenticado y el libro está en el catálogo.

Flujo principal:

  1. El bibliotecario escanea el código del libro.
  2. El sistema muestra los datos y verifica disponibilidad.
  3. El bibliotecario escanea la credencial del alumno.
  4. El sistema verifica que no haya multas ni préstamos vencidos.
  5. El sistema registra el préstamo con devolución a 14 días.
  6. El sistema imprime el comprobante.

Flujo alternativo 4a: si el alumno tiene multas, el sistema muestra el monto y bloquea el préstamo.

Postcondición: el libro queda marcado como prestado y el alumno suma un préstamo activo.

3.4 · Especificación

Especificación de requerimientos

Escribir los requerimientos de manera precisa, completa y verificable. El documento se llama SRS (Software Requirements Specification), normado por el estándar IEEE 830.

◆ Tipos de requerimientos

Funcionales: qué debe hacer el sistema. "El sistema debe permitir registrar un préstamo."

No funcionales: cómo debe comportarse. "El registro debe completarse en menos de 2 segundos con 100 usuarios concurrentes."

De dominio: restricciones del campo de aplicación. "Se aplican las disposiciones del Reglamento de Bibliotecas."

Formato EARS para redactar sin ambigüedad

  • Ubicua: "El sistema DEBE <comportamiento>".
  • Activada por evento: "CUANDO <evento>, el sistema DEBE…"
  • No deseada: "SI <condición>, ENTONCES el sistema DEBE…"
  • Estado: "MIENTRAS <estado>, el sistema DEBE…"
  • Opcional: "DONDE <característica habilitada>, el sistema DEBE…"
3.4 · Calidad

Un buen requerimiento tiene 7 atributos

AtributoSignificaEjemplo negativo
CompletoNo falta información para implementarlo"El sistema debe notificar." ¿A quién?
No ambiguoUna sola interpretación posible"Debe ser rápido." ¿Qué es rápido?
VerificableSe puede probar si se cumple"Debe ser intuitivo." ¿Cómo se mide?
ConsistenteNo contradice otros requerimientosUno dice 5 años, otro dice 3
TrazableTiene ID único y se puede rastrearLista sin numeración
NecesarioSi se elimina, se pierde valor real"El botón debe ser azul" (es diseño)
FactiblePosible con tiempo y recursos"Predecir el clima con 100%"
✓ Antipatrones a evitar
  • Verbos vagos: "manejar", "procesar". Usa: registrar, validar, calcular.
  • Adjetivos sin métrica: "amigable", "robusto". Si no lo mides, no lo verificas.
  • Mezclar qué con cómo: "usar MySQL" limita opciones de diseño.
  • Requerimientos compuestos: "el sistema debe X y Y". Sepáralos.
3.5 · Validación

Revisión y validación

◆ Distinción esencial

Verificación: ¿estamos construyendo el producto correctamente? Revisa que el documento esté bien hecho.

Validación: ¿estamos construyendo el producto correcto? Revisa que los requerimientos reflejen lo que el cliente realmente necesita.

Cinco técnicas de validación

  1. Revisión formal con el cliente — sección por sección del SRS.
  2. Prototipado — maquetas o versiones funcionales limitadas que el cliente pueda "tocar".
  3. Casos de prueba derivados — uno por cada requerimiento; si no se puede escribir, el requerimiento no es verificable.
  4. Validación con escenarios — recorrer cada caso de uso narrando la historia.
  5. Walkthroughs e inspecciones — reuniones estructuradas con roles definidos.
▲ Criterios de aceptación (estilo BDD)

RF-03: Si el alumno tiene multas pendientes, bloquear préstamos.

Dado un alumno con multa de $50, cuando el bibliotecario intente el préstamo, entonces el sistema muestra "Préstamo bloqueado: multa de $50" y no crea el registro.

3.6 · Gestión

Gestión de requerimientos

Los requerimientos cambian: el negocio evoluciona, los usuarios descubren necesidades, surgen restricciones técnicas. Gestionar es controlar este flujo sin perder el rumbo.

Priorización · técnica MoSCoW

▲ MVP de biblioteca

Must (indispensable): registrar préstamo, devolución, autenticar, consultar catálogo.

Should (debería): calcular multas, enviar recordatorios por correo.

Could (podría): reservar desde portal, recomendaciones según historial.

Won't (esta versión): integración con otras universidades, app móvil nativa.

Estados del ciclo de vida

  • Propuesto → alguien lo sugirió, no se aprueba aún.
  • Aprobado → fue revisado y aceptado para la línea base.
  • En desarrollo → está siendo implementado.
  • Implementado → el código está escrito y compila.
  • Verificado → pasó pruebas internas.
  • Validado → el cliente lo aceptó.
  • Rechazado o diferido → no se implementa o se posterga.
3.7 · Control de cambios

Control de cambios

Los cambios son inevitables, pero deben ser controlados. Un cambio mal gestionado es la primera causa de retrasos y sobrecostos.

Proceso típico

  1. Solicitud de cambio (Change Request): descripción, justificación, solicitante.
  2. Análisis de impacto: qué requerimientos, módulos, pruebas se afectan.
  3. Decisión del CCB (Comité de Control de Cambios): aprueba, rechaza o difiere.
  4. Implementación: actualizar SRS, casos de uso, pruebas y código.
  5. Verificación y cierre del Change Request.

Trazabilidad

◆ Tres direcciones

Hacia atrás: del requerimiento hacia su origen (quién lo solicitó, en qué reunión).

Hacia adelante: hacia los artefactos derivados (diseño, código, pruebas).

Horizontal: entre requerimientos del mismo nivel (qué dependencias existen).
